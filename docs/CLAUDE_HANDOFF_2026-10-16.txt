ACTUAL STRUCTURES, NOT THE OLDER PROPOSED CONTRACT NAMES

The strict interpretation schema currently requires:
  version=1; baseHash(64characters);
  scopes[]: id, label, kind(call|scenario|quotation-rule), parentId, evidence;
  operations[]: scopeId, field, operation, string value, unit, evidence;
  tasks[]: id, scopeId, kind, source, charges[], ruleScopeIds[], evidence;
  unresolved[]: scopeId, question, evidence, taskIds[];
  inputIds[] identifying authenticated inputs.
Evidence is {inputId, quote}; referenced quote must occur in an allowed input.
Operations: assert, correct, reject, preserve, reference, uncertain, inherit.
Task kinds: quote, rule, elapsed, arithmetic, facts, comparison, other.
Source categories at this interface: official, supplied, none.
There are separate optional comparison IDs/mode and auxiliary-action fields.

ConversationState stores version/hash/revision/scopes/facts/tasks/unresolved/consumed.
Facts retain evidence, unit, operation, revision, supersession and status:
established, conflicting, superseded, reference or rejected. Facts can include a
distinct lookup source class. Scenario inheritance checks parent scope and vessel
identity. Current explicit user facts take precedence over later lookup facts.
Hashing uses SHA256 of JSON serialization in this implementation; do not assume
the more elaborate canonical-hash contract from old design prose is implemented.

The actual ConversationAnswer contains a run binding, context hash, per-task
items, questions and a complete flag plus digest. Items retain dependencies,
pending conditions, source class, body, calculation and optional scoped totals.
Session verification recomputes the planned answer and compares digests. This is
not evidence that a universal independent semantic validator exists.

The old contracts.md explicitly labels proposed interfaces such as CallContextV1,
TariffRuleV1 and AnswerV1. Do NOT mistake every proposed interface/table/operation
there for an implemented class or database table. Current types above are the
concrete serving implementation, which still uses regex/heuristic validation in
several places. "Shared architecture" does not mean all regex or legacy code is gone.
